> 何时读我：崩溃归因、混合栈归属、APM 崩溃数据分析。
> 不适用：OOM（无崩溃日志）→ oom-memory.md；白屏 → white-screen.md。
> 必须先有：堆栈、dSYM/UUID、影响面五维、APM 导出数据。
> 产出：影响面分级 + 堆栈分层解析 + 根因假设 + 闭环验证。

分析 APM 输出的崩溃、异常、性能数据时，严格按以下流程，禁止直接扎入单条堆栈盲目排查（参考 Sentry / Crashlytics 业界标准）。

#### 1. 崩溃问题分析四步法

1. **影响面评估**

   - 按异常类型、堆栈指纹、App版本、iOS版本、机型五个维度聚合
   - 确认：用户量级、发生频次、首次出现版本、趋势走向
   - 分级：P0 大面积崩溃 / P1 特定场景集中 / P2 零星个案

2. **上下文提取**

   - 必取字段：前后台状态、内存水位、CPU占用、运行时长、网络状态、电池电量
   - 场景信息：当前页面、用户操作路径、是否首次启动、是否后台唤醒
   - 系统信息：系统版本、机型、内存总大小、是否低内存机型

3. **堆栈分层解析**

   - 先判定异常大类：Mach异常 / Signal信号 / NSException / JS异常
   - 再看核心线程：崩溃线程 + 主线程 + 子线程关键状态
   - 区分归属层：系统层 / 原生基建层 / 桥接层 / RN框架层 / 业务层
   - 模式匹配：优先匹配已知典型模式（空指针、野指针、死锁、越界、OOM）

4. **根因验证与闭环**

   - 提出根因假设后，必须匹配上下文证据
   - 修复后必须对应到 APM 指标变化，验证修复效果

---

#### 3. 混合栈问题归属判定

1. 异常类型为 JS 报错 → 优先排查 RN 业务层与框架层
2. 异常类型为原生崩溃，且栈顶在 RN 桥接层 → 优先排查桥接通信与参数传递
3. 异常类型为原生崩溃，且栈顶在原生基建 → 优先排查原生层
4. 无明确异常的白屏/卡死 → 按「系统→原生→桥接→RN」逐层排查
